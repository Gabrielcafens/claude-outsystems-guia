Client e Server Actions

0%

Praticamente toda questão desse tópico é a mesma pergunta disfarçada: de que lado da rede isso roda? Client Action roda no navegador, compilada para JavaScript. Server Action roda no servidor, compilada para .NET. Entre as duas existe uma requisição HTTP — e é aí que moram as pegadinhas.

As quatro caixas que a prova mistura

TipoOnde rodaOnde viveParâmetros
Client ActionNavegadorAba LogicInput, Output e locais
Screen / Block ActionNavegadorDentro da Tela ou BlocoSem Output, só locais
Server ActionServidorAba LogicInput, Output e locais
Data ActionServidorDentro da Tela ou BlocoOutput que alimenta a tela

Client e Server Actions globais têm Input, Output e variáveis locais Q26. Screen Action é local à tela e não tem Output Parameter — é armadilha frequente.

O livro-razão: o que existe de cada lado

Cliente

Client · Screen · Block Action

  • Widgets e propriedades de runtime — Form1.Valid, Input1.ValidationMessage
  • Variáveis locais da tela ou bloco
  • Client Variables (navegador)
  • Nó JavaScript
  • Nó Message
  • Nó Destination (navegar)
  • Refresh Data
  • Chamar outra Client Action
  • Chamar uma Server Action Q25

Não tem SQL, Entity Actions, Aggregate dentro do fluxo, Cache in Minutes, Site Properties, CheckRegisteredRole Q122.

Servidor

Server · Data Action

  • Aggregate e nó SQL
  • Entity Actions: CreateX, UpdateX, CreateOrUpdateX, GetX, DeleteX
  • Site Properties
  • Chamar outra Server Action
  • Propriedade Cache in Minutes

Não tem JavaScript, Message, Destination, widgets, Client Variables — e não consegue chamar uma Client Action Q25.

A regra de ouro

A seta é sempre cliente → servidor, nunca o contrário. Se a questão propõe uma Server Action que mostra uma Message, navega, ou marca um input como inválido, a alternativa está errada sem precisar ler o resto.

O fluxo canônico de salvar um registro

// Screen Action: SalvarOnClick (navegador) Start → If Form1.Valid True → Run Server Action SalvarCliente(Cliente) ← 1 ida ao servidor → Message "Cliente salvo" → Destination ClienteList False → End // Server Action: SalvarCliente (servidor) Start → CreateOrUpdateCliente(Cliente) → End devolve o Id Q106

Function = Yes

Marcar Function = Yes permite usar a action dentro de expressões, e obriga a action a ter exatamente um Output Parameter Q99. Função client só vale em expressões client-side; função server só em expressões server-side.

Armadilhas

01

"Basta arrastar o CreateOrUpdateCliente para a Screen Action."

Não. Entity Actions só aparecem na toolbox de uma Server Action ou Data Action.

02

"Três Run Server Action em sequência dentro de uma Client Action."

Cada um é uma requisição HTTP separada, com conexão e transação próprias. A correção oficial é compor tudo numa Server Action só — a OutSystems cataloga isso como dívida técnica de performance.

03

"Chamo uma Server Action no On Initialize."

Os eventos de ciclo de vida são serializados na requisição — a chamada segura o render. Em blocos, a documentação avisa que o render pode começar antes da action terminar.

04

"Uso CheckRegisteredRole() numa Client Action."

Não dá Q122. As actions de Role são server-side. Numa tela você usa nas propriedades de permissão; na lógica, dentro de Server Action.

05

"Data Action e Server Action são a mesma coisa."

Data Action pertence à tela, dispara junto com os Aggregates ao carregar e você reexecuta com Refresh Data. Server Action é reutilizável e você invoca com Run Server Action.

Fluxos Lógicos

0%

Regras estruturais

  • Um único Start, vários Ends Q27. Todo caminho precisa chegar num End — ramo solto é erro de validação.
  • If: exatamente duas saídas, True e False. Não dá para adicionar mais ramos Q28d Q23b. Os dois ramos são obrigatórios, e um If pode fechar um laço improvisado.
  • Switch: avaliado de cima para baixo, só o primeiro True executa Q29b. O ramo Otherwise é obrigatório e pega o resto.
  • For Each: itera uma lista Q114. Não precisa de condição de parada — a lista acaba. O conector Cycle é o laço; Start Index diz de onde começar.
  • Assign: várias atribuições num nó só, de cima para baixo.
Pegadinha do Switch

Duas condições verdadeiras não fazem o fluxo passar pelas duas. Vale a que estiver mais acima. Exemplo da Q117: N = 2000, ramo 1 é N < 1000, ramo 2 é N > 1000 → executa o ramo 2, e o Otherwise nunca roda para esse valor.

A cadeia de exceções, na ordem

Quando uma exceção é lançada, o fluxo atual é interrompido e a execução recomeça no handler mais específico para aquele tipo Q31 — não no primeiro que aparecer, e não em todos. A busca segue esta ordem:

  1. Exception Handler no próprio fluxo. Pode haver vários num mesmo action Q30a, e nenhum é obrigatório Q30b. O que não pode é o fluxo do handler cruzar outro fluxo Q30c.
  2. Sobe para quem chamou. Estourou na Action B e não tratou? Quem trata é a Action A que a invocou.
  3. On Exception do UI Flow a que a tela pertence.
  4. Global Exception Handler da aplicação — por padrão, o On Exception do UI Flow Common.

As três exceções à cadeia

  • Em fluxos que começam num Timer, só o Exception Handler dentro da própria lógica resolve. Sem ele, a execução para e o erro só vai para o log.
  • OnApplicationReady não é coberto pelo Global Exception Handler.
  • Exceção vinda de integração (REST, extensão): você não consegue determinar o tipo. Use All Exceptions e leia ExceptionMessage.
Aggregate vazio não é exceção

Um Aggregate que não encontra registros devolve lista vazia — não lança nada. Se a questão fala em RecordNotFound, é porque alguém escreveu um If .List.Empty → Raise Exception na mão.

Armadilhas

01

"O Exception Handler continua o fluxo de onde parou."

Não continua. O fluxo é interrompido e recomeça no handler. O que vinha depois do nó que estourou não roda.

02

"Com vários handlers, o erro vai para todos / vai direto pro Global."

Vai para um só: o mais específico Q31. Se existe um Database Exception e o erro é de banco, ele ganha do All Exceptions.

03

"Adiciono um terceiro ramo no If."

If tem dois ramos, ponto. Precisa de mais? É Switch.

04

"O For Each precisa de uma condição de parada."

Não precisa Q114. Ele percorre a lista até o fim. Para sair antes, ligue para um nó fora do ciclo.

Usando Blocos

0%

Um Block é um pedaço de UI com lógica própria reaproveitado em várias telas. Tem variáveis, client actions, aggregates e eventos de ciclo de vida. O que ele não tem é o que a prova cobra.

O que o bloco tem e o que não tem

  • Input Parameters — o dado desce do pai para o bloco.
  • Não existe Output Parameter em bloco. Para devolver algo, o caminho é Evento.
  • Pode ser instanciado em Telas e em outros Blocos — menos nele mesmo Q64 Q92. Sem recursão.
  • Bloco não é destino de navegação — não pode ser o On Click Destination de um botão Q96.
  • Placeholders reservam espaço a ser preenchido quando o bloco é instanciado Q65. Existem só em Blocos, podem ser vários, e preenchê-los não é obrigatório.
  • Mudou o bloco, mudou em todas as instâncias Q63c — dentro do mesmo módulo. Vindo de outro módulo, atualize a dependência Q112.

Ciclo de vida

EventoQuandoPai × filho
On InitializeAntes de renderizar e antes de buscar dados. Use para valor default de variável local Q70—
On ReadyDOM pronto. Primeiro momento seguro para JavaScriptBloco antes do pai
On RenderApós o Ready e a cada mudança de dadosBloco antes do pai
On Parameters ChangedSó em bloco. Quando o pai muda um inputBloco externo antes do aninhado
On DestroyAntes de sair do DOMTela → bloco externo → aninhado
Duas pegadinhas juntas

1. On After Fetch não é evento de Tela nem de Bloco Q69 — ele pertence ao Aggregate ou à Data Action. Os eventos da tela são Initialize, Ready, Render e Destroy, nessa ordem Q71.

2. On Parameters Changed dispara quando o pai altera o input. Mudança feita dentro do próprio bloco não dispara Q68. É o ponto do gabarito furado da Q119 — veja a errata.

Navegando entre telas, a ordem é: Init, Ready e Render da tela nova, e só então o Destroy da antiga. A tela velha só morre depois que a nova renderizou — por isso os dois DOMs coexistem por um instante.

Caso de uso canônico: o bloco recebe FiltroData e tem um Aggregate que depende dele. Quando o pai muda a data, o On Parameters Changed roda e chama Refresh Data. Sem isso, o parâmetro muda e a lista continua igual.

Armadilhas

01

"Adiciono um Output Parameter no bloco."

Não existe. Bloco só tem entrada. A saída é evento.

02

"O pai renderiza primeiro, depois os blocos."

Invertido. Em On Ready e On Render o bloco vem antes. Só o On Destroy é de cima para baixo.

03

"Mudei o input, o Aggregate do bloco recarrega sozinho."

Não recarrega. A UI reage a dados, mas rodar a query de novo é explícito: Refresh Data.

04

"Coloco o bloco dentro dele mesmo para fazer uma árvore."

Não pode Q64. Telas e outros blocos, sim; ele mesmo, não.

Eventos de Blocos

0%

Evento é a única forma de um bloco falar com quem o contém. Parâmetro desce, evento sobe — essa frase resolve boa parte das questões.

O que a Q66 cobra

Eventos só podem ser definidos no Bloco, nunca na Tela. A alternativa "eventos podem ser definidos no nível do Block ou da Screen" é a falsa da Q66. Tela não define evento — tela trata evento.

As três peças

  1. Definir — dentro do bloco. Botão direito no bloco → Add Event. O evento pode ter Input Parameters: são os dados que sobem.
  2. Disparar — na lógica do bloco. O nó Trigger Event notifica o pai de que algo relevante aconteceu no escopo do bloco Q93.
  3. Tratar — na tela pai. Selecione a instância do bloco e, em Events, aponte a propriedade Handler para uma Screen Action.

Duas instâncias do mesmo bloco podem usar o mesmo handler para o mesmo evento Q66d. E definir handler só é obrigatório quando o evento está marcado como Is Mandatory Q67.

Bloco falando com bloco irmão

Bloco A — Trigger Event → Tela pai — muda Input Parameter → Bloco B ↓ Bloco B reage no On Parameters Changed

Exemplo completo: bloco de busca

// No bloco SearchBar Evento: OnSearch(TextoBusca Text) // Client Action do bloco, no OnClick da lupa Start → Trigger Event OnSearch(TextoBusca: SearchInput) → End // Na tela: propriedade Handler da instância → OnSearchHandler Start → Assign FiltroTela = TextoBusca → Refresh Data GetProdutos → End

Armadilhas

01

"Uso o evento para receber um valor de volta do pai."

Evento não tem output. Ele carrega dados só para cima. Para o pai responder, ele muda um input do bloco — e aí é On Parameters Changed.

02

"O bloco chama diretamente a Screen Action da tela."

Não alcança. O bloco não conhece quem o usa — é isso que o torna reutilizável.

03

"Trigger Event serve para a tela avisar os blocos filhos."

Ao contrário Q93. Trigger Event vai sempre de baixo para cima: do bloco para o pai. De cima para baixo, é input parameter.

04

"Preciso de handler porque o evento tem input parameters."

Não. Só é obrigatório quando o evento é mandatory Q67.

Entidades e Entidades Estáticas

33%

Entity

  • O Id nasce Long Integer + Auto Number, mas pode ser modificado Q123b. O que é obrigatório é ser um único atributo — não existe chave composta Q86c.
  • Para chave alternativa ou composta, use Index. Index único ajuda a evitar duplicação Q43c.
  • Entidade precisa de identificador para participar de relacionamento Q39.
  • Entity Actions geradas: CreateX, UpdateX, CreateOrUpdateX, GetX, DeleteX. Não existe RetrieveX Q14. CreateOrUpdate devolve o Id do registro Q106.
  • Service Studio infere o tipo pelo nome do atributo: HouseNumber vira Integer sozinho Q13.
  • Mapeamento: Entity→Tabela, Atributo→Coluna, Index→Index. Reference attribute é Foreign Key, não Primary Key Q11.
A que mais cai

Mandatory = Yes é validado na interface — mas no banco a coluna continua aceitando null. Não há validação de obrigatoriedade no nível do banco.

Static Entity

  • Conjunto fixo de valores — o equivalente a uma enumeração Q17. Contém um conjunto de Records Q15.
  • Quatro atributos automáticos: Id, Label, Order, Is_Active — e não é obrigatório preencher os quatro em cada registro Q16a.
  • Somente leitura em runtime. Registros só entram e saem em tempo de desenvolvimento.
  • Referência em expressão: Entities.Priority.Low Q115. Para exibir o texto num dropdown, Options Text = Color.Label Q95.
  • Pode ser convertida de/para Entity comum: botão direito → Advanced.

Validações de Formulários

33%

Camada 1 — built-in

  • Com Built-in Validations = Yes no botão, a plataforma valida duas coisas e só duas: campos obrigatórios preenchidos e tipo de dado compatível Q94.
  • Tamanho máximo de texto NÃO é validação built-in Q50.
  • Só vale para widgets dentro do widget Form.
  • Campo obrigatório ganha a dica visual automática no Label Q48d — não escreva o asterisco à mão.
  • Campo inválido: o widget continua visível, ganha estilo próprio (borda vermelha) e a mensagem aparece Q49.
Se built-in estiver desligado

Com Built-in Validations = No, a plataforma não valida nada e Form.Valid continua True mesmo com obrigatórios vazios. Nesse cenário, se você não setar Valid à mão, o formulário passa direto.

Camada 2 — customizada, sempre client-side

PropriedadeO que faz
Form1.ValidBooleano do formulário — é o que você testa antes de salvar
Input_X.ValidBooleano daquele campo
Input_X.ValidationMessageTexto sob o campo — só aparece quando .Valid é False
// 1. validações customizadas primeiro (OnChange ou no início da action) Assign Input_ConfirmarSenha.Valid = (Senha = ConfirmarSenha) Input_ConfirmarSenha.ValidationMessage = If(Senha = ConfirmarSenha, "", "As senhas não conferem") Form1.Valid = Form1.Valid and (Senha = ConfirmarSenha) // 2. o teste do Form vem DEPOIS da última validação customizada — Q51 Start → If Form1.Valid True → Run Server Action SalvarUsuario → Message → Destination False → End

A ordem é o que a Q51 cobra: o Form.Valid é checado depois da última validação customizada. Checar antes não enxerga o que você acabou de invalidar.

A regra que resolve o tópico

Server Action não enxerga widget. Todo assign de .Valid e .ValidationMessage tem que estar numa Client Action. Se a regra depende do banco — "esse e-mail já existe?" — a Server Action devolve um Boolean, e o assign nos widgets acontece de volta no cliente.

Widgets que caem junto

  • Checkbox e Switch ligam a variável Boolean Q47.
  • Para ler o que o usuário digitou, use a variável ligada ao input, não InputName.Value Q48c.
  • No Button Group, a propriedade Variable fica no grupo, não em cada item Q46c.
  • O Variable de um dropdown de Users é do tipo User Identifier Q120.
  • Bloco não pode ser On Click Destination de um botão Q96.

Group By e funções de agregação

Aqui está o erro que o seu material de revisão trouxe invertido. Ao aplicar Sum, Count, Max, Min ou Average, o output do Aggregate traz apenas as colunas agrupadas e as agregadas Q62b Q87 Q109. Os demais atributos ficam cinza e não entram no resultado Q62d.

"Quantos pedidos por prioridade?" → Group By em Priority.Id e Count em Order.Id Q89. Você pode aplicar várias funções de agregação no mesmo Aggregate.

Não confunda com coluna escondida

Esconder uma coluna à mão afeta só o preview Q60. Coluna cinza por causa da agregação sai do output. Duas regras diferentes, e a prova pergunta as duas.

As abas do Aggregate

  • Sources — de quais Entities buscar Q32.
  • Filters — condições. Todos os filtros são concatenados com AND, viram WHERE no SQL, e um registro precisa satisfazer todos Q33a.
  • Sorting — pode ter vários critérios, com direções diferentes, mas é obrigatório definir a direção de cada um Q34. Ordenar por Data e depois por Nome = Nome só desempata datas iguais Q111.
  • Test Values — só para testar o preview Q35. O resultado do Test Query pode divergir do runtime.

Atributos calculados aceitam atributos das entidades, funções built-in traduzíveis para SQL e variáveis — mas não aceitam Server Actions Q61.

Fetch, Refresh e propriedades de runtime

  • O padrão de Fetch é At Start, não On Demand Q72c.
  • Com Fetch = Only On Demand, o aggregate só roda via Refresh Data numa Screen Action Q73.
  • Screen Aggregates rodam assíncronos e em paralelo Q36a, e existem só no escopo da tela.
  • O On After Fetch dispara para todo Aggregate, independente do Fetch Q72d.
  • Ligar dados a uma Table ou List: setar a propriedade Source do widget para a saída do Aggregate Q37.
RuntimeTipoO que é

.Count é o total real no banco; .List.Count conta só o que veio, limitado por Max. Records. Mostrar "1" quando deveria ser "123" é exatamente esse erro — foi o bug que você já caçou no seu próprio app.

Paginação e ordenação em Table

  • Max. Records da paginação = registros por página Q78 Q107. Start Index é o índice do primeiro registro, não o número da página.
  • Trocou de página e a tabela não muda? Falta o Refresh Data do Aggregate no OnNavigate Q103.
  • Ordenação em Table: o evento On Sort recebe a coluna clicada como parâmetro Q79 — não é automático.
  • List não tem On Sort embutido; use outros widgets para o usuário escolher o critério Q80.

Aggregate × SQL Tool

  • Subqueries só no SQL Tool Q82. Joins e Group By existem nos dois.
  • Sintaxe do SQL avançado: {Entity}.[Attribute] Q81.
  • Em SELECT, prefira Structure como output — traz menos atributos e menos dados Q83.
